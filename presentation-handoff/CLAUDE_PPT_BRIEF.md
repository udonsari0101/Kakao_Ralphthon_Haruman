## 0. Claude에게 바로 전달할 요청

이 폴더의 자료로 **한국어 3분 발표용 PPT 6장**을 만들어 주세요. 핵심은 **사고 싶은 상품을 담고 → 잠시 기다리고 → 다시 결정한 결과가 마당에 남는 실제 앱 흐름**입니다.

- 결과물: 16:9 비율의 편집 가능한 PPTX와 슬라이드별 발표자 노트. 가능하면 PDF 미리보기도 제공해 주세요.
- 시간: 아래 배분대로 **총 180초**. 기능 나열보다 핵심 흐름 하나를 처음부터 결과까지 보여 주세요.
- 이미지는 **실제 연결 Android 스마트폰에서 기본 글꼴 크기로 촬영한 일반 앱 화면만** 사용합니다. 에뮬레이터·격리 테스트 fixture·글자 확대 검수용 화면은 사용하지 않습니다.
- 실제 캡처의 UI·데이터를 새로 만들거나 합성하지 마세요. 제공 로고를 사용하고 화면 비율을 유지해 주세요.
- 한 장에 핵심 문장 하나, 보조 문구 2~3개 이내. 자세한 설명은 발표자 노트에 넣어 주세요.
- 촬영된 실제 등록·대기 화면과 기존 결정 기록으로 구성합니다. 없는 화면이나 가정한 시연을 추가하지 마세요.
- **검증된 기능·설명용 예시·구현 중인 마지막 동작**을 아래 사실표에 따라 구분합니다.

이 문서는 발표 인계용이며, 앱 개발·실제 결제·설정 변경을 지시하는 문서가 아닙니다.

## 1. 발표 기준과 핵심 메시지

심사 기준은 [원본 PDF](reference/student-preparation.pdf)와 [추출 텍스트](reference/student-preparation-extracted.txt)에 있습니다. 발표는 **① 문제와 해결책 → ② 핵심 유저 플로우 시연 → ③ AI에 맡긴 일과 확인한 방법**의 순서로 구성합니다.

| 평가 항목 | 이 발표의 근거 |
| --- | --- |
| 문제 정의 | 사고 싶은 순간과 실제 필요를 판단하는 순간 사이에 생각할 시간을 만들려는 문제 |
| 해결 방식의 차별성 | 링크 보관에서 기다림·재결정·마당 기록으로 이어지는 경험 |
| 결과물의 완성도 | 실제 상품 API 응답, 실폰 저장·수정·결정 흐름 |
| AI에 일을 맡기는 능력 | 원하는 동작과 초안·기존 데이터 보존 조건을 함께 전달한 사례 |
| AI 결과를 판단하는 능력 | 실제 경로를 재현하고 수정 후 재검수·회귀 테스트로 확인한 사례 |

> **하루만은 사고 싶은 마음을 잠시 보관하고, 다시 고른 결정을 마당에 남기는 앱이에요.**

문제는 팀이 해결하려고 설정한 가설입니다. 사용자 조사나 소비 감소 효과가 입증됐다고 표현하지 않습니다. 친근한 해요체를 사용하고, 소비를 비난하거나 구매를 유도하지 않습니다. 앱의 서비스 표현은 **‘상품 링크’**로 통일합니다.

### 1장 — 사고 싶은 순간, 바로 결정해야 할까요?

**핵심 문장:** 사고 싶은 마음과, 정말 필요한지는 다를 수 있어요.

**본문:** `하루만` / `마음은 담아 두고, 결정은 잠시 뒤로` / `상품 링크를 보고 바로 사고 싶어지는 순간`

**화면 자리:** 왼쪽에 질문과 로고, 오른쪽에 `01-vault-real-products.png`. 가짜 사용자 사진이나 통계는 필요 없습니다.

**발표자 노트·20초:** “상품 링크를 보다가 갑자기 사고 싶어진 경험이 있죠. 저희는 그 순간의 마음과 실제로 필요한지를 판단하는 순간 사이에 시간을 만들고 싶었어요. 하루만은 사고 싶은 상품을 잠시 담아 두고, 다시 생각할 수 있게 만든 앱이에요.”

**연결:** “그래서 상품을 담은 다음의 경험을 이렇게 만들었어요.”

### 2장 — 마음을 담고, 하루 뒤 다시 골라요

**핵심 문장:** 링크를 보관하는 데서, 다시 선택하는 경험까지 이어져요.

**본문:** `상품 링크 담기 → 하루 기다리기 → 다시 결정하기 → 마당에 기록`

**화면 자리:** 네 단계의 간단한 텍스트·아이콘 흐름과 `08-yard-final.png`. 보조 설명은 `기본 24시간`과 `안 사기 = 나무 / 구매 결정 = 구덩이`입니다.

**발표자 노트·25초:** “하루만에서는 링크를 담고 기본 하루 뒤에 다시 결정해요. 안 사기로 한 선택은 나무가 되고, 구매 결정은 구덩이로 남아요. 기록을 주별 마당에서 돌아볼 수 있어요. 단순히 상품을 모으는 것에서 한 걸음 더 나아가, 기다리고 다시 고르는 흐름을 연결했어요.”

**연결:** “실제 상품 링크 하나로 보여드릴게요.”

### 3장 — 링크 하나로 담고, 정보를 확인해요

**핵심 문장:** 상품 링크에서 가져온 정보를 확인하고, 필요하면 고쳐요.

**본문:** `상품 링크 → 상품명·가격·이미지 확인 → 보관함에 저장` / `실제 4개 상품 링크 등록 확인`

**화면 자리:** `02-api-product-confirm.png`와 `03-product-saved.png`를 최대 두 화면으로 배치합니다. `05-product-waiting-detail.png`는 등록 후 대기 설명에 사용합니다. 자막은 **`실제 상품 등록 · 기본 24시간 대기`**입니다.

**발표자 노트·40초, 화면 전환 포함:** “실제 폰에서 상품 링크를 등록한 화면이에요. API에서 가져온 이름과 가격, 이미지를 확인하고, 필요하면 정보를 고친 뒤 보관함에 저장해요. 네 개 상품을 각각 한 번씩 등록해 확인했어요. 새 상품은 기본 하루를 기다리게 되고, 상세 화면에서 남은 시간을 볼 수 있어요. 다음은 이미 결정이 남아 있는 기존 기록으로 보여드릴게요.”

**촬영된 흐름:** 상품 링크 입력 → 반환 필드 확인·필요 시 수정 → `보관함에 저장` → 저장 완료 → 24시간 대기 상세. 기존 결정 기록을 이 새 상품의 즉시 결정 결과처럼 이어 붙이지 않습니다.

**연결:** “이미 안 사기로 결정한 기록은 마당에 어떻게 남아 있을까요?”

### 4장 — 안 사기로 한 선택이 나무가 돼요

**핵심 문장:** 다시 고른 선택이 마당에 남아요.

**본문:** `안 사기로 한 기존 기록 → 나무가 있는 마당 → 주별로 돌아보기` / `새 등록 상품과 다른 기존 기록 예시`

**화면 자리:** `12-saved-decision-detail.png`와 `13-yard-week.png`, 필요하면 `08-yard-final.png`. 12는 기존 ‘초콜릿’ 상품의 안 사기 기록입니다. 현재 표시 가격과 결정 당시 금액은 별개일 수 있어요. 새로 등록한 11번가 상품의 연속 결정 장면이 아닙니다.

**발표자 노트·35초, 화면 전환 포함:** “방금 등록한 상품은 아직 기다리는 중이라, 이미 저장된 다른 결정 기록을 보여드릴게요. 이 초콜릿 상품은 안 사기로 결정한 기록이에요. 이런 선택은 마당에 나무로 남고, 주별로 돌아볼 수 있어요. 마당의 금액은 결정 당시의 상품 금액이며 실제 계좌에서 확인한 절약액은 아니에요.”

**촬영된 흐름:** 기존 결정 상세 → 마당의 나무 → 주별 마당. 아직 촬영하지 않은 결정 버튼 조작이나 시간 경과를 시연했다고 말하지 않습니다. 구덩이 제거와 예시 그래프는 이 핵심 설명 중간에 끼워 넣지 않습니다.

**연결:** “이 흐름을 만드는 과정에서도, AI가 만든 결과를 그대로 끝내지 않았어요.”

### 5장 — AI에 맡긴 뒤, 같은 경로로 다시 확인했어요

**핵심 문장:** 동작 조건을 맡기고, 데이터 보존과 실제 화면을 기준으로 판단했어요.

**대표 사례:** 수정창을 닫은 뒤 상품 추가를 누르면 이전 수정창이 다시 열리던 문제.

| 맡긴 일 | 전달한 조건 | 확인·판단 |
| --- | --- | --- |
| 새 상품 추가와 기존 상품 수정 분리 | 새 추가는 빈 입력, 미저장 수정 초안 보존, 기존 상품 유지 | 실제 경로 재현 → 수정 → 같은 조작 재검수·회귀 테스트 |

**화면 자리:** `맡기기 → 확인하기 → 고치고 재검증`의 세 칸. 제공되지 않은 버그 전후 화면이나 로그를 만들지 않습니다.

**발표용 요약 지시:** “수정창을 닫고 상품 추가를 누르면 새 입력을 열어 주세요. 이전 수정 초안과 기존 상품은 보존하고, 같은 경로의 회귀 테스트로 확인해 주세요.” 실제 대화의 원문 인용처럼 표시하지 않습니다.

**발표자 노트·40초:** “AI에는 화면 구현뿐 아니라 수정 조건과 검증까지 맡겼어요. 예를 들어 수정창을 닫고 새 상품을 추가했는데 이전 수정창이 다시 열리는 문제가 있었어요. 새 입력은 비우되, 이전 수정 초안과 기존 상품은 보존하라고 조건을 구체화했어요. 이후 같은 경로를 실폰에서 다시 확인하고 회귀 테스트를 추가했어요. 생성된 코드보다 실제 동작과 데이터가 유지되는지를 판단 기준으로 삼았어요.”

**근거·노트 전용:** 앱 소스의 `ui/HarumanViewModel.kt` 내 `openAdd`, 계측 테스트 `ui/AddAfterEditUiTest.kt`. 소스는 이 발표 폴더 밖에 있으며 PPT 제작에 필수인 첨부는 아닙니다. ‘한 번에 완성’, ‘모든 버그 해결’이라고 말하지 않습니다. AI 도구로 실행한 검증을 사람이 직접 수행한 것처럼 바꾸지 않습니다.

### 6장 — 사고 싶은 마음에, 생각할 시간을

**핵심 문장:** 하루만, 마음은 담아 두고 선택은 다시 해요.

**본문:** `실제 상품 링크 등록` / `기다림 → 결정 → 마당` / `AI와 구현하고, 실폰에서 확인`

**화면 자리:** 제공 로고와 최종 `08-yard-final.png` 한 장. 여기서 새 기능·로드맵·테스트 숫자를 펼치지 않습니다.

**발표자 노트·20초:** “하루만은 실제 상품 링크를 담는 순간부터, 기다리고 결정한 결과가 마당에 남는 흐름을 만들었어요. AI에 조건을 구체적으로 맡기고 실폰 결과를 확인하면서 완성도를 높였어요. 사고 싶은 마음에 생각할 시간을 주는 앱, 하루만이에요. 감사합니다.”

## 5. 시연 준비와 지연 시 대안

1. 제공된 실폰 캡처 순서로 발표를 준비합니다. 새 4개 상품은 24시간 대기 상태이며, 기존 결정 기록은 별도 사례라고 설명합니다.
2. 캡처를 위해 기존 상품을 바꾸거나 시간을 강제로 진행시키지 않습니다. 촬영되지 않은 동작은 시연 장면으로 만들지 않습니다.
3. 기본 글꼴의 실폰 캡처만 사용하고, 알림·개인 식별 정보·인증 설정 화면을 발표에서 제외합니다.
4. API가 늦으면 “이 부분은 실제 폰에서 확인한 화면으로 이어서 보여드릴게요”라고 말하고 준비된 캡처로 전환합니다. 실패한 요청을 성공했다고 말하지 않습니다.
5. 녹화는 실제로 제공되고 출처가 확인된 경우에만 사용합니다. 없는 영상·가짜 성공 화면을 만들지 않습니다.
6. 조작 시간을 포함해 180초로 리허설합니다. 반복 재시도로 시간을 소모하지 않고 결정 결과까지 보여줍니다.

**주발표에서 제외:** 예시 그래프의 긴 설명, 구덩이 제거의 긴 시연, 인증정보·비공개 주소·원문 응답·기기 식별자·개발 로그. 사용자 수·소비 감소율·실제 절약 효과·처리 속도 등 확인하지 않은 숫자를 만들지 않습니다. 구덩이 기능을 질문받으면 **실제 결제는 없으며 앱 내부 구덩이 제거·재실행 보존을 확인함**이라고 설명합니다.

## 8. 최종 인계 상태

1. **화면:** 08~13은 최종 실폰 캡처로 갱신했습니다. 09·10의 제거 흐름은 선택 자료이고 주발표의 상품 등록→기다림→결정 기록을 우선합니다.
2. **마지막 동작:** 구덩이 제거·재실행 보존·행복 토리·탭 문구 변경을 확인했습니다. 제거 당시9개 상품의 다른 필드와 구매 금액은 보존됐습니다. **실제 결제는 없습니다.**
3. **QA·배포:** 최종 [RC3 QA](reference/QA_TERRACE_RC3.md)와 실제 APK·배포 상태를 확인합니다. 본문에 테스트 숫자나 배포 상태가 없어도 발표는 완성됩니다.
4. **최신 자료:** `SCREENSHOTS.md`와 `MANIFEST.md`를 확인합니다. 초기 README나 이전 계획과 충돌하면 최신 실측 QA와 최종 촬영 설명을 따릅니다.

이 폴더만 전달받아도 위 구성과 문안으로 제작할 수 있습니다. 소스 저장소가 추가 제공되면 `GOAL_SPEC.md`, `UI_CHARACTER_DESIGN.md`, `ASSET_PLAN.md`를 선택적으로 참고하되, 과거 계획과 미검수 기록을 현재 완료 사실로 옮기지 않습니다.
